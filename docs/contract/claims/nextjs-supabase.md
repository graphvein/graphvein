# Claim contract: Next.js and Supabase

The claim contract tables for Next.js routes, server actions and Supabase (ADR 0077) as
recorded when the feature was designed (task T024, internal record). The code tables in
`internal/index`, `internal/extract/schema`, `internal/extract/models/supabasetypes` and
`internal/extract/tableaccess` are kept 1:1 with these rows by their contract tests.

## Claim contract: Next.js routes (T024a, rows NX)

Assumptions:

- **NX-V1** Routing is the file-system routing of the app and pages
  directories plus the literal `rewrites` read by NX-P3: `middleware.ts` /
  `proxy.ts`, non-literal `rewrites`, `redirects` and `headers` are not
  applied. Shown on every link to a Next.js route (`assumes: ["NX-V1"]` on
  the linked `client_call`, since edges carry no attributes).
- **NX-V2** A `next.config` wrapped in plugin calls (`withNextIntl(config)`,
  `withA(withB(config))`) keeps the `basePath`, `trailingSlash` and `pageExtensions` of the object
  it wraps.
- **NX-V3** (T024a2) An afterFiles or fallback rewrite applies only when
  no page and no `public/` file serves the call's original path: Graphvein
  checks the project's route handlers and Pages Router API files, not its
  pages or public files. Shown on calls such a rewrite re-routes
  (`assumes: ["NX-V1", "NX-V3"]`).

## Claim contract: server actions (T024b, rows SA)

Model per O1 (a) (decided): one level-4 `server_action` node
per action (`transport: server_action`, `contains` from the declaring file
or function, `exposes_action` fact edge from the action function), and, per use, an
`action_call` node contained by the calling owner with a `calls_action`
edge to the action (T024b clarification: edges carry no attributes, so a
use's `form` and `boundary` are attributes of its node, as Tauri's
`ipc_call`), shown in the API section as a third transport next to HTTP and
Tauri IPC.

## Claim contract: Supabase (T024c, rows SB)

Assumptions:

- **SB-V1** The database the client talks to is the one the repository's
  Supabase migrations describe (as TA-V1): every SB edge is `inferred`.
- **SB-V2** The Supabase platform provides the objects of the prelude
  (`auth`, `storage`, `extensions`, `realtime`, `vault` schemas; roles
  `anon`, `authenticated`, `service_role`); user migrations do not replace
  them. The migration session's search_path is the platform's
  `"$user", public, extensions` (NX-F2: SB-M10 resolves unqualified
  extension types through it; the oracle's prelude sets it).
- **SB-V3** (T024c1b) A `supabase/migrations` directory without
  `supabase/config.toml` whose entries all follow the CLI's name pattern
  holds Supabase CLI migrations ("read as Supabase CLI migrations; no
  supabase/config.toml found"), shown in the schema view.
- **SB-V5** (T024c1b R1) Inserts into Supabase platform tables
  (`storage.buckets`) succeed on a fresh project, and the platform's
  triggers change no object of the set; shown in the schema view with the
  statement ("inserts into Supabase platform tables (storage.buckets)
  succeed on a fresh project, and the platform's triggers change no object
  of the set: <statement>").
- **SB-V4** (T024c1b) Supabase platform: the extensions `http` and
  `vector` are available to the migration role (Supabase lets its
  `postgres` role create them through supautils; "Supabase platform:
  extension X is available to the migration role", shown in the schema
  view per extension the set creates). Verification `mapped`: Supabase's
  allow-list is not published on a reachable host, so the list holds the
  extensions the corpora create, each checked by replaying the corpus on
  PostgreSQL 17 with the PGDG builds of the extension.

- **SB-V6** (T024c3) A generated types file (SB-G1) was generated from
  the database the client talks to and is current; it is the package's
  schema source only when the package has no Supabase migration set
  (`assumes: SB-V6` on the SB edges into its tables).
