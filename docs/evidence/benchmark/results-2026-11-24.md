# Agent benchmark results, 2026-11-24 (baseline, rounds 2 and 3)

The first full run of the agent benchmark: three coding agents each
answered the 21 frozen questions in [questions.jsonl](questions.jsonl), once
with their own file tools only (`base`) and once with the Graphvein MCP
server attached (`mcp`), three repetitions per agent. Method, prompt, limits
and grading: [method.md](method.md). Answers are graded by a script against
facts verified from the source code; no language model judges an answer.

Data: [`runs/2026-11-24-full/`](runs/2026-11-24-full/) (manifest, one row per
attempt in `runs.jsonl`, final answers, generated
[`summary.md`](runs/2026-11-24-full/summary.md)). Every number on this page
is computed from `runs.jsonl`; where a run was attempted more than once, its
last row is its result.

**Correction (2026-11-24, after the run): BQ-18 re-graded.** The expected
answer of BQ-18 missed one call site,
`src/frontend/src/controllers/API/queries/flows/use-get-flow.ts:22`, which
sends `GET /api/v1/flows/{flow_id}` whenever its `public` flag is false
(details under "Wrong runs"). The call site was added to
[questions.jsonl](questions.jsonl) (the row's `correction` field records
it) and the committed answers were graded again with
`gvbench regrade` (method.md, "Corrections"). Only the 18 BQ-18 runs
changed; each keeps its original grade in `grade_v1`. All numbers on this
page use the corrected grades. Before the correction, BQ-18 was 0/3 in every
cell and the correct totals were Claude Code 53/63 and 59/63, Codex 56/63
and 56/63, opencode 55/63 and 56/63 (base and mcp).

A second round on the same day, [`runs/2026-11-24-r2/`](runs/2026-11-24-r2/),
added Codex with its Graphvein tools visible (a non-default configuration,
see "Round 2") and re-ran the five opencode runs stopped by the old per-run
cost ceiling and the three opencode base BQ-16 runs that had invalid

## Reading

Three repetitions of 21 questions is a small sample: per question a
difference of one run out of three is within run-to-run variation, and the
per-run spread (the min-max columns) is wide. Nothing below goes beyond
these runs, these models and these two corpora.

**Correctness.**

- Claude Code: 53/63 correct in base mode and 62/63 with Graphvein (mean F1
  0.947 to 0.998). The whole difference is on langflow (20/30 to 29/30):
  BQ-15 0/3 to 3/3, BQ-16 2/3 to 3/3, BQ-18 0/3 to 3/3, BQ-21 0/3 to 2/3.
  No question had fewer correct runs with Graphvein. Claude Code called a
  Graphvein tool in all 63 mcp runs.
- Codex: 59/63 in both modes. Codex called a Graphvein tool in only 2 of its
  63 mcp runs (one `endpoint` call in BQ-1 repetition 2, one `table` call in
  BQ-9 repetition 3); in the other 61 it answered with shell commands only.
  So the Codex mcp column is, in practice, a second base column, and says
  nothing about Graphvein's effect on Codex (round 2 measures Codex with
  the tools visible). Codex's JSON output does not
  report whether an MCP server started (`mcp_server_status` is
  `unreported` in all 126 Codex rows); the two calls show the server was
  connected in those two runs, and the rows cannot tell whether it was
  connected in the other 61. A likely reason, from the Codex 0.171.0
  source and its `codex features list`: when the model supports tool search
  (the bundled catalog says `gpt-6.2-sol` does), Codex defers every MCP tool
  behind that search instead of listing it, and the feature that does this
  (`tool_search_always_defer_mcp_tools`) is marked "removed" and fixed on,
  so `--disable` cannot turn it off. The `codex-visible` variant of round 2
  shows the tools (see "Round 2").
- opencode: 56/63 to 59/63 (mean F1 0.931 to 0.958); a Graphvein tool was
  called in 53 of 63 mcp runs. The difference is three runs: BQ-18 (1/3 to
  3/3), BQ-2 and BQ-16 (one each), against one fewer on BQ-4.

**Tokens, tool calls, cost.**

- Claude Code with Graphvein used half the tool calls (863 to 436 in total;
  median 8 to 5) and 38% fewer output tokens (150k to 94k), but more cache
  reads (median 17k to 38k; higher on 17 of 21 questions). The billed cost
  was nearly the same: $9.85 base and $9.65 mcp for 63 runs each (median
  $0.087 and $0.079 per run; mcp cheaper on 12 of 21 questions, dearer on
  9). The largest saving was BQ-21 (median 143 to 23 tool calls, $1.21 to
  $0.93); the largest increases were the langflow route-callers questions
  BQ-15 to BQ-17, where the mcp runs were also the ones that got BQ-15 and
  BQ-16 right.
- opencode with Graphvein used 32% fewer tool calls (1,025 to 701) and 33%
  fewer output tokens (100k to 68k), and its recorded cost fell from $0.077
  to $0.056 for 63 runs; on langflow the median tool calls fell from 18.5
  to 10.5.
- Codex: within a few percent in every metric, as expected from 2 Graphvein
  calls.

**Wall time.** Medians are close in every pair (Claude 20.8 s and 20.6 s,
Codex 20.4 s and 19.2 s, opencode 18.6 s and 21.9 s). Totals: Claude 1,796 s
base and 1,906 s mcp (slower with Graphvein on langflow: median 21.2 s to

## Run notes

### Pilots

Four one-question pilots (BQ-1, one repetition, both modes, all three
agents) ran before the full run on the same day; their data is kept as
committed and is **not** part of the results above:
[`2026-11-24-p0`](runs/2026-11-24-p0/), [`p1`](runs/2026-11-24-p1/),
[`p2`](runs/2026-11-24-p2/), [`p3`](runs/2026-11-24-p3/). Each found a
problem in the driver, which was fixed before the next one.

- **Before p0: symbolic links.** The FastAPI template contains 4 symbolic
  links. Windows cannot create them without developer mode (and dangling
  ones not at all), so exporting the workspace failed there; the driver
  now leaves symbolic links out of every workspace, on every system, and
  records how many it skipped (`symlinks_skipped` in the manifest). p0 and
  every later run used this.
- **p0: Codex's built-in apps server and OpenRouter usage lag.** All three
  base-mode Codex attempts called Codex's built-in ChatGPT apps MCP server
  `codex_apps` (GitHub search, file fetch, web run) and were recorded as
  invalid ("an MCP server was present in base mode"). The driver now runs
  Codex with `--disable` for its built-in apps, plugins, browser and similar
  tool sources. In the same pilot both opencode rows were booked at $0
  billed although opencode reported a cost: the OpenRouter key usage had not
  moved yet. The driver now books the larger of the key's usage delta and
  opencode's own reported cost.
- **p1: Codex code-mode tools.** Base-mode Codex now listed MCP resources
  through its own internal server named `codex`, which the parser counted as
  an MCP server, so all three attempts were again invalid. These built-in
  code-mode tools are now counted as ordinary tool calls (`codex/...`), not
  as an MCP server. Per-agent repetition counts (`--agent-reps`) were added
  at the same time.
- **p2: Windows sandbox.** Codex's base run answered `unknown:0`: it ran no
  shell command, because Codex's read-only sandbox on Windows rejected every
  command without a configured Windows sandbox. The driver now passes
  `-c windows.sandbox="unelevated"` on Windows and puts Codex's bundled
  ripgrep on `PATH`, as Codex's own launcher does.
- **p3:** all six runs answered BQ-1 correctly; Codex ran shell commands in
  both modes (it did not call Graphvein in its mcp run). The full run used
  the same driver commit.

### Invalid attempts

Ten attempts, all opencode base mode (BQ-16 nine times over its three
repetitions, BQ-18 once), were recorded as `invalid` because a `read`,
`grep` or `glob` call failed with a permission error; the rows do not record
the error text. The cause is in the driver's opencode configuration:
opencode 1.19.6's built-in agent asks before a tool touches a path outside
the workspace (`external_directory`) and before a third identical tool call
in a row (`doom_loop`), the configuration left both at "ask", and
`opencode run` rejects every ask, which fails the tool call with "The user
rejected permission to use this specific tool call". Which of the two
applied to each attempt cannot be told from the rows. The driver now denies
`external_directory` outright (a refused path is expected and leaves the run
valid), allows `doom_loop`, and records the error text of any other denial in
the row's `detail`. An invalid run is retried at most twice; BQ-16 repetitions
2 and 3 were still invalid after their retries, and the `--resume` pass
started them again (repetition 2 then answered on its first new attempt,
repetition 3 on its second). Their results above are those last attempts;
the invalid attempts are in `runs.jsonl` and are not graded.

### The five `cost_cap` runs

All five are opencode on BQ-21 (base repetitions 1-3, mcp repetitions 2-3).
The driver stopped them at the $0.45 per-run ceiling, which prices every
step at the highest endpoint price over all providers with no caching. Their
recorded costs were $0.0034-0.0061 each: by the time the bound reached
$0.45 they had run 14-21 steps, 48-109 tool calls and 82-131 s, with
636k-724k cache-read tokens against 39k-59k uncached input tokens. They count as wrong (score 0). The
ceiling did its job of bounding the worst case, but at these cache rates it
stops runs far below their real cost; that is a limit of this run, not a
model failure. The per-run bound now prices cache-read tokens at the highest
cache-read price of any endpoint ($0.03 per million instead of $0.60); the
first of these runs would have been bounded at about $0.10 instead of
$0.48 (method.md, "OpenRouter cost control"). Round 2 re-ran all five under
the new bound; none was stopped (section "Round 2").
